# P2 — Discovering a VXLAN (RFC 7348)

Two hosts believe they sit on the same LAN, even though a routed network
separates them. VXLAN builds that illusion by wrapping the hosts' Ethernet
frames inside UDP packets and tunnelling them between the two routers. In P2
this is **pure Linux kernel** work (`ip link` / `bridge`) — FRR does nothing
here; the control plane only matters in P3.

## Topology

The two routers are NOT cabled directly — each router's `eth0` plugs into a
GNS3 **Ethernet switch** (`Switch_wil` in the subject), which is the shared
underlay segment. The switch is a built-in GNS3 device (not one of our images).

```
                          Switch  (badass-switch)
                          ┌──────────┐
                       e0 │          │ e1
                    ┌─────┘          └─────┐
                    │ eth0            eth0 │
              _login-1                    _login-2
             (badass-router)            (badass-router)
              VTEP 10.1.1.1              VTEP 10.1.1.2
                    │ eth1            eth1 │
              _login-1_host              _login-2_host
               30.1.1.1/24                30.1.1.2/24
```

- **Underlay** `10.1.1.0/24`: the real segment between the two VTEPs, carried
  through the switch. This is where the encapsulated UDP/4789 packets travel.
- **Overlay** `30.1.1.0/24`: what the hosts see — one virtual L2 segment
  stretched between them by **VXLAN VNI 10** through bridge **br0**.

> as you wish"), so the exact numbers are free — `10.x` underlay / `30.x`

## Key terms

- **VTEP** (VXLAN Tunnel EndPoint): the device that encapsulates/decapsulates —
  here, each router. For the overlay it acts as a plain L2 switch, NOT a router.
- **VNI** (VXLAN Network Identifier): the 24-bit segment ID in the VXLAN header
  (16 million possible vs a VLAN's 4096). Ours is **10**.
- **Underlay**: the real routed/switched network carrying the UDP packets.
- **Overlay**: the virtual L2 segment the hosts live in, on top of the underlay.
- **BUM traffic**: Broadcast, Unknown-unicast, Multicast — the frames a switch
  must flood. How a VTEP floods (to one peer vs to a group) is the whole
  static-vs-multicast distinction.

## What is a bridge, and why we set one up

A **Linux bridge is a software Ethernet switch** living inside the router's
kernel. Everything a physical switch does, `br0` does — its "ports" are just
interfaces on the machine instead of RJ45 sockets.

```
ip link add br0 type bridge      # create the virtual switch
ip link set eth1    master br0   # port 1: cable to the host
ip link set vxlan10 master br0   # port 2: the VXLAN tunnel
```

Once created, `br0` behaves as a 2-port switch: it forwards frames between its
ports, **learns MAC addresses** from source addresses (that's the
`bridge fdb show` table), and **floods** unknown/broadcast frames.

**Why we need it:** on the router, `eth1` (facing the host) and `vxlan10` (the
tunnel) are two independent interfaces — nothing passes frames between them by
itself. We must connect them at L2:

- Giving them IPs and routing → wrong: that makes the router a *router* for the
  overlay, the host would need a gateway, and the two hosts would land on
  different subnets. The subject wants them on the *same* segment, no gateway.
- Putting both into a bridge → right: they become two ports of one switch, so a
  frame from the host is switched onto the tunnel and vice-versa.

```
        ROUTER 1 (VTEP)
     ┌────────────────────────┐
     │      br0 (switch)       │
     │    ┌──────┴───────┐     │
   eth1 ─┤port         port├─ vxlan10 ──► UDP 4789 tunnel to Router 2
     │   (to host1)   (tunnel)│
     └────────────────────────┘
```

So the bridge is the glue that makes the router behave as a **switch** for the
overlay, not a router. Stitching Router1's `br0` to Router2's `br0` through the
tunnel gives the two hosts a single, stretched Ethernet segment.

Order note: an interface can only be enslaved to a bridge that already exists,
so create `br0` before `ip link set ... master br0`. `vxlan10` itself can be
created before or after — what matters is that by the end both `eth1` and
`vxlan10` are `master br0` and everything is `up`.

## How the bridge decides where to forward (two-layer lookup)

The bridge does NOT have a rule like "eth1 → vxlan10". Nothing tags a frame as
"for the tunnel". There are **two separate forwarding decisions**, both driven
by the **destination MAC**.

**Layer 1 — `br0` picks an outgoing port.** When a frame arrives on `eth1`,
`br0` looks at its destination MAC in the bridge FDB (`bridge fdb show`):

- **MAC known** (learned earlier) → send out only that one port. If host2's MAC
  is recorded behind `vxlan10`, it goes out `vxlan10`.
- **MAC unknown, or broadcast/multicast (BUM)** → **flood**: copy out every port
  except the incoming one (so an `eth1` frame goes out `vxlan10`).

The bridge learns from **source** MACs: every frame arriving on `vxlan10`
teaches it "that source MAC lives behind the `vxlan10` port".

**Layer 2 — `vxlan10` picks a remote VTEP.** The `vxlan10` port is not a wire —
it's a tunnel driver that must decide *which VTEP IP* to encapsulate toward. It
has its **own** table, the VXLAN FDB (`bridge fdb show dev vxlan10`):

- **inner MAC known** → unicast-encapsulate to that specific remote VTEP IP.
- **inner MAC unknown / BUM** → use the catch-all `00:00:00:00:00:00` entry:
  - **static**: `remote 10.1.1.2` → unicast to that one hardcoded VTEP.
  - **multicast**: `group 239.1.1.1` → send to the group so every VTEP receives it.

The VXLAN driver also learns: an encapsulated frame from VTEP `10.1.1.1` teaches
it "inner-MAC X is reachable via `10.1.1.1`" — that's flood-and-learn filling
the VXLAN FDB.

First ping (`host1 → ping 30.1.1.2`), step by step:

```
1. host1 has no MAC for host2 → ARP broadcast (dst ff:ff:ff:ff:ff:ff)
2. Frame enters R1 on eth1.
3. br0: destination is broadcast → FLOOD → out vxlan10.
4. vxlan10: broadcast = BUM → catch-all entry:
      static    → unicast-encapsulate to 10.1.1.2
      multicast → send to group 239.1.1.1
   Outer packet (src 10.1.1.1, dst .2/group, UDP 4789, VNI 10) crosses the switch.
5. R2 decapsulates and LEARNS: host1's MAC via 10.1.1.1 (vxlan FDB) and
   behind the vxlan10 port (bridge FDB).
6. br0 on R2 floods the ARP out eth1 → host2 replies with its MAC (unicast).
7. Reply returns the same way; both sides have now learned each other's MAC in
   both tables. Every later packet is unicast — no more flooding.
```

So a frame reaches `vxlan10` either because the bridge **flooded** it
(unknown/broadcast) or because the bridge earlier **learned** host2's MAC is
behind that port — and then a second lookup inside the VXLAN driver chooses the
remote VTEP. That is why you show **both** tables at defense:

- `bridge fdb show` → which **port** (eth1 vs vxlan10) a MAC is behind.
- `bridge fdb show dev vxlan10` → which **remote VTEP IP** a MAC is reachable
  through.

Both start nearly empty and fill after the first ping — that flood-then-unicast
transition is the flood-and-learn behaviour the subject wants demonstrated.

## The switch vs the bridge — NOT the same thing

A common confusion: the `Switch_wil` in the picture is **not** an illustration
of `br0`. They are real, separate devices on different layers.

| | `Switch_wil` | `br0` (×2) |
|---|---|---|
| How many | one, in the middle | one **inside each** router |
| Layer | underlay (`10.1.1.x`) | overlay (`30.1.1.x`) |
| Carries | encapsulated UDP/4789 packets | the hosts' raw Ethernet frames |
| Role | connects the two routers | connects host-port ↔ tunnel-port |
| Visible | its own icon in GNS3 | hidden inside the router node |

```
   host1 ─┐                                                    ┌─ host2
          │eth1                                            eth1│
     ┌────┴─────┐                                      ┌───────┴──┐
     │ br0 (R1) │                                      │ br0 (R2) │
     └────┬─────┘                                      └────┬─────┘
        vxlan10                                          vxlan10
          │  encapsulate                     decapsulate  │
        eth0 ──────► Switch_wil (underlay 10.1.1.x) ◄───── eth0
                    carries the UDP/4789 packets
```

The picture therefore contains **three** switching elements: the real switch in
the middle (underlay) plus a `br0` hidden inside each router (overlay). Delete
`Switch_wil` and the VTEPs lose their path to each other — it has a very real
role. With only two routers you *could* replace it with a direct cable and
static mode would still work, but the subject uses a switch because it is a true
shared L2 segment — which is what **multicast mode** needs to flood BUM traffic,
and it scales to the 4 VTEPs in P3.

## Interface names are slot labels, not roles

`eth0` / `eth1` are just adapter-slot names GNS3 assigns by order — there is **no
rule** that "eth0 faces the host." The role of each interface is decided by which
cable you plugged into which slot, so the config must match *your* wiring.

In the subject's setup (which our config files assume):

- **Router `eth0` → the switch** (proof: the subject's Wireshark title reads
  `routeur_wil-1 eth0 to Switch_wil`). So `eth0` = underlay: it gets `10.1.1.x`
  and is the `dev` of the `vxlan10` line.
- **Router `eth1` → the host** → enslaved into `br0`, no IP.
- On the **host**, the subject uses `eth1` (`ifconfig eth1 ... 30.1.1.1`) — a
  different slot number on a different device, which just proves the names are
  arbitrary per node.

Think in **roles**, not numbers:

- interface cabled to the **switch/underlay** → `10.1.1.x` + `dev` for vxlan10
- interface cabled to the **host** → `master br0`, no IP

If your wiring is reversed (e.g. `eth0` to the host), just swap the two names in
the config — nothing else changes. To check on a real node: hover the link end
in GNS3 for its label, or run `ip -d link show` and correlate MACs with the
links.

## Static vs multicast — the two modes you deliver

The topology never changes between modes; only the one `vxlan10` creation line
differs, because the two modes answer one question — *"when the switch must
flood BUM traffic, flood to whom?"*

- **Static** (`remote 10.1.1.2`): the peer VTEP is hardcoded — BUM traffic is
  unicast to it; scales to exactly one peer per interface.
- **Multicast** (`group 239.1.1.1`): VTEPs join `239.1.1.1`; BUM traffic is
  multicast to the group, peers are discovered dynamically, remote MACs learned
  from traffic (**flood & learn**). `239.0.0.0/8` is the admin-scoped multicast
  range. This is exactly the mechanism P3 replaces with BGP EVPN control-plane
  learning.

## Demo sequence (defense)

1. Build topology with the P1 images, apply the `_s` configs + host configs.
2. `ping 30.1.1.2` from host 1 → works.
3. Capture on the **router↔switch** link (subject uses `routeur-1 eth0 →
   Switch`): ICMP encapsulated in **UDP 4789 / VXLAN, VNI 10**
   (filter: `udp.port == 4789`). Outer IP `10.1.1.1→10.1.1.2`, inner IP
   `30.1.1.1→30.1.1.2`. The hosts' link shows plain ICMP — encapsulation
   happens at the VTEP.
4. Switch to multicast: `ip link del vxlan10` on both routers, apply `_g`
   configs. Show `ip -d link show vxlan10` → `group 239.1.1.1`.
5. Ping again, then show the MAC table on both routers:
   `bridge fdb show dev vxlan10` (remote host MACs learned via the tunnel —
   the subject's "mac address table" screenshot).

## The three "money shots" for the evaluation

- Wireshark on the router↔switch link: ICMP inside UDP 4789 / VNI 10 (the onion:
  outer Eth → outer IP `10.1.1.x` → UDP 4789 → VXLAN VNI 10 → inner Eth → inner
  IP `30.1.1.x` → ICMP).
- `ip -d link show vxlan10`: shows `remote 10.1.1.2` (static) or `group
  239.1.1.1` (multicast).
- `bridge fdb show dev vxlan10`: remote host's MAC learned through the tunnel.

## Gotchas

- `dstport 4789`: without it Linux uses legacy port 8472 and Wireshark won't
  decode VXLAN automatically.
- Console-typed `ip` commands do NOT survive a node restart — reapply the
  config file (that's why the commented files are the deliverable). Swapping the
  `_s` ↔ `_g` file live is exactly the multicast switch-over you do at defense.
- MTU: VXLAN adds 50 bytes of headers; with default 1500 everywhere a full-size
  overlay frame won't fit the underlay. Fine for ping demos; raise the underlay
  MTU to 1550 if large transfers ever misbehave.
- Interface names must match your wiring (see "Interface names" above).
